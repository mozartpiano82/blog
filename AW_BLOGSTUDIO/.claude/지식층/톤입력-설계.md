# 톤 입력 설계 — 사용자가 뭘 가져오든 받아낸다

> **전제.** 학원장은 "블로그 글 5편을 텍스트로 준비"할 수 없다.
> 글이 아예 없을 수도 있고, PDF·워드·카톡 캡처로 흩어져 있을 수도 있다.
> **입력을 사용자에게 맞추는 것이 이 제품의 온보딩 성패를 가른다.**

---

## 0. 가장 먼저 — 카톡과 블로그는 같은 말투가 아니다

이걸 놓치면 제품이 망가진다.

| | 카톡 | 블로그 |
|---|---|---|
| 문장 | 짧게 끊음, 여러 줄로 나눔 | 한 문장이 완결 |
| 종결 | 생략 많음 ("네", "그쵸") | 완결형 |
| 이모지 | 많음 | 거의 없음 |
| 존대 | 상대에 따라 요동 | 일정 |

**카톡 말투를 그대로 블로그에 쓰면 이상한 글이 된다.**
그래서 두 소스에서 **뽑는 것을 다르게** 한다.

| 소스 | 뽑는 것 | 안 뽑는 것 |
|---|---|---|
| **블로그·글** | 문장 길이 분포, 종결어미 비율, 쉼표 밀도, 문단 구조 | — |
| **카톡·대화** | **어휘**, **호칭**, **자주 쓰는 표현**, **태도**(사과·칭찬·거절 방식) | 문장 길이, 종결어미 비율, 문단 구조 |

> **규칙 TI-1.** 카톡만 있는 사용자에게는 문장 길이·종결어미 목표치를 **만들지 않는다.**
> 대신 어휘·호칭·표현 사전을 만들고, 문장 구조는 **기본 프리셋**을 쓴다.
> 톤가이드에 "구조 지표는 미확보" 라고 명시한다.

## 1. 받는 입력 (우선순위 순)

| 순위 | 입력 | 얻는 것 | 최소 |
|---|---|---|---|
| 1 | **블로그 글** (형식 무관) | 구조 + 어휘 전부 | 1편부터 |
| 2 | **학부모 안내문·문자** | 구조 일부 + 어휘 + 호칭 | 5건 |
| 3 | **카톡 대화** | 어휘·호칭·표현·태도 | 200줄 |
| 4 | **직접 말하기** (없을 때) | 최소 프리셋 선택 | — |

### 지원 형식

| 형식 | 처리 |
|---|---|
| 붙여넣기 | 그대로 |
| `.txt` `.md` | 그대로 |
| `.pdf` | `pdftotext` (런처 동봉) |
| `.docx` | zip 해제 → `word/document.xml`에서 텍스트 추출 (라이브러리 불필요) |
| `.hwp` `.hwpx` | **hwpx만 지원** (zip+xml). 구형 hwp는 "다른 이름으로 저장 → PDF" 안내 |
| 카톡 `.csv` (PC 내보내기) | `Date,User,Message` 컬럼 |
| 카톡 `.txt` (모바일 내보내기) | 안드로이드/iOS 두 포맷 정규식 |
| 블로그 URL | 본문 추출 (스크랩 수집기 재사용) |

> **규칙 TI-2.** 지원 못 하는 형식이 오면 **막지 말고 우회로를 준다.**
> "이 파일은 못 읽습니다"가 아니라 "PDF로 저장해서 다시 주시면 됩니다"라고 말한다.

## 2. 카톡 — 누구 말을 분석할 것인가

원장님이 지적한 그 문제다. 카톡은 **여러 사람의 말이 섞여 있다.**

### 처리 순서

```
① 참여자 목록과 발화 수를 뽑는다
② 원장 계정을 자동 추정한다
③ 추정 결과를 사용자에게 보여주고 확인받는다   ← 자동 확정하지 않는다
④ 선택된 화자의 발화만 남기고 나머지는 버린다
⑤ PII 마스킹 후 분석
```

### ② 자동 추정 — 3개 신호

| 신호 | 방법 | 신뢰도 |
|---|---|---|
| **기초정보 대조** | `raw/01_기초정보/`의 원장 이름과 참여자명 일치 | 높음 |
| **1:N 구조** | 단톡방에서 혼자만 여러 방에 공통 등장 | 중간 |
| **역할 어휘** | "숙제", "수업", "상담", "안내드립니다" 발화 비중이 높은 쪽 | 중간 |

> **규칙 TI-3.** 발화 수가 가장 많은 사람을 원장으로 **가정하지 않는다.**
> 학부모가 더 많이 말하는 방도 흔하다.

### ③ 확인 화면 — 반드시 사람이 고른다

```
이 대화에서 누구의 말투를 분석할까요?

  ▸ 김선주  (412줄)  ← 원장님으로 추정됩니다
      "숙제 안 해온 친구는 오늘 남아서 하고 갑니다"
      "어머님, 지난주보다 확실히 나아졌어요"

    김○○ 학부모  (287줄)
      "선생님 오늘 늦을 것 같아요"

    이○○ 학부모  (95줄)

  [김선주 선택]  [다른 사람]  [여러 명 합치기]
```

**샘플 발화 2개를 함께 보여준다.** 이름만 보고는 못 고른다.

> **규칙 TI-4.** 이름이 "나", "Me", 빈칸으로 나오는 내보내기가 있다.
> 이 경우 샘플 발화만으로 고르게 한다.

## 3. PII 마스킹 — 분석 전에 반드시

카톡에는 학부모 이름·전화번호·아이 성적이 그대로 있다.
**개인정보보호법 문제이자, 글에 새어나가면 사고다.**

| 대상 | 처리 |
|---|---|
| 전화번호 | `010-****-****` |
| 이름 (2~4자 + 호칭) | `○○○ 어머님` |
| 학교명 | `○○중학교` |
| 주소·동 이름 | `○○동` |
| 점수·등수 | 유지 (톤과 무관하지만 통계에 필요) → **단 글에는 못 나감** |
| 계좌·주민번호 | 전체 삭제 |

> **규칙 TI-5.** 마스킹 결과를 **원장님이 눈으로 확인하는 화면**을 반드시 거친다.
> 자동 마스킹은 100%가 아니다. "이 중 놓친 개인정보가 있나요?"를 묻는다.

> **규칙 TI-6.** 원본 카톡 파일은 `raw/03_내가쓴글_대화/원본/`에 두고,
> **마스킹본만 분석과 wiki 편입에 쓴다.** 원본은 밖으로 안 나간다.

## 4. 표본이 부족할 때 — 막지 않는다

**"5편 없으면 못 씁니다"는 최악의 온보딩이다.**

| 확보량 | 신뢰도 | 처리 |
|---|---|---|
| 글 5편 이상 | **높음** | 전체 지표 사용 |
| 글 2~4편 | **중간** | 지표 사용 + 톤가이드에 "표본 부족" 표시 |
| 글 1편 | **낮음** | 어휘·호칭만 사용. 구조는 프리셋 |
| 글 0편, 카톡만 | **낮음** | 어휘·호칭·표현만. 구조는 프리셋 |
| 아무것도 없음 | — | **프리셋 선택** (아래) |

### 프리셋 — 아무 자료도 없을 때

원장님 강의 자료에서 뽑은 학원 블로그 문체 3종. 사용자가 **예시 문단을 보고 고른다.**

| 프리셋 | 성격 | 예 |
|---|---|---|
| **A. 담백한 정보형** | 합쇼체, 짧은 문장, 표·목록 많음 | "중2 서술형 감점은 세 가지에서 나옵니다." |
| **B. 대화하듯 친근형** | 해요체, `거든요`·`더라고요`, 인용 많음 | "상담하다 보면 이런 질문 받거든요." |
| **C. 차분한 상담형** | 해요체+합쇼체 혼용, 긴 문장, 완화 표현 | "물론 모든 아이에게 맞는 방법은 아닙니다." |

> **규칙 TI-7.** 프리셋으로 시작해도 **글을 발행할 때마다 학습한다.**
> 원장이 고친 부분을 `raw/03_내가쓴글_대화/`에 쌓아 다음 분석에 반영한다.
> **온보딩에서 완벽할 필요가 없다.**

## 5. 기계 판독 블록 — **실측값을 그대로 적는다**

톤 분석이 낸 숫자는 여기로 들어가야 뜻이 생긴다. 이 블록이 없으면 검수기는
**모든 원장님께 같은 기본값**을 들이댄다. 그게 이 프로그램이 하려는 일의 반대다.

`10_학원위키/톤가이드.md` 안에 **정확히 이 모양으로** 넣는다.

```json 목표치
{
  "stdevMin": 14,
  "concentrationMax": 45,
  "commaPerSentMax": 0.5,
  "formalMaxPct": 5,
  "signatureMinPct": 8
}
```

| 열쇠 | 무엇 | 어떻게 정하나 |
|---|---|---|
| `stdevMin` | 문장 길이 표준편차 **하한** | 실측의 60% (밑돌면 AI 티) |
| `concentrationMax` | 30~50자 집중도 **상한** | 실측 + 10%p |
| `commaPerSentMax` | 문장당 쉼표 **상한** | 실측 + 0.3 |
| `formalMaxPct` | 합쇼체 **상한** | **실측 + 5%p** |
| `signatureMinPct` | 거든요·더라고요 **하한** | **실측의 절반**. 실측이 0이면 0 |

### 원장님이 합쇼체로 쓰신다면 그게 맞다

**규칙 TI-2.** 실측 합쇼체가 기본값(5%)을 넘으면 **실측을 따른다.**
79%로 쓰시는 분께 5%를 요구하면 매 글이 반려되고, 고쳐 봐야 **원장님 글이 아니게 된다.**
학부모에게 어떤 어미로 말할지는 원장님이 정하실 일이다.

> 프로그램이 원장님께 하는 말(화면 문구)은 **언제나 해요체**다. 그건 안 바뀐다.
> 여기서 정하는 건 **원장님이 학부모께 하시는 말**이다. 둘은 다른 것이다.

### 열쇠 이름을 지어내지 않는다

**규칙 TI-3.** 위 다섯 개 말고 다른 이름을 쓰면 **조용히 무시된다.** 오류도 안 난다.
`formalMax`, `합쇼체상한` 같은 것을 쓰면 기본값이 그대로 남고, 아무도 모른다.
자신이 없으면 그 열쇠를 아예 빼라 — 빠진 것은 기본값을 쓴다.

### 자료가 모자라면 만들지 않는다

`TI-1`(카톡만 있을 때)에 걸리면 `stdevMin` `concentrationMax` `commaPerSentMax`
`formalMaxPct` 를 **빼고** 나머지만 적는다. 없는 근거로 숫자를 지어내면
검수기가 엉뚱한 것을 반려한다.


## 6. 편집으로 배운 것 — 이 섹션이 없으면 학습이 새 나간다

초기 톤 분석은 원장님이 **뭘 쓰시는지**를 알려준다.
편집은 **뭘 싫어하시는지**를 알려준다. 뒤쪽이 훨씬 강한 신호다.

전에는 그 관찰을 `10_학원위키/원장님.md` 에 적었다. 그런데 **그 파일을 읽는
에이전트가 하나도 없었다.** `/피드백` 이 쓰기만 하고 아무도 안 읽었다.
원장님이 매번 고쳐주셔도 다음 글은 똑같이 나왔다. 배운 게 글에 닿지 않았다.

**그래서 톤가이드 안에 넣는다.** writer 와 polisher 가 이미 읽는 파일이다.
새 파일을 만들면 또 고아가 된다.

`10_학원위키/톤가이드.md` 맨 끝에 **정확히 이 모양으로** 둔다.

```
## 편집으로 배운 것

<!-- /피드백 이 갱신한다. 사람이 손으로 고쳐도 된다. -->

- 첫 문단이 길면 두 문장으로 쪼개신다 (3편에서 관찰)
- 질문으로 끝나는 맺음말을 지우신다 (2편)
- 사례 뒤에 바로 숫자를 붙이는 걸 좋아하신다 (2편)
```

### 규칙

**규칙 TI-6.** 한 줄에 관찰 하나. **몇 편에서 봤는지 괄호로 적는다.**
1편짜리 관찰은 적지 않는다 — 그 글에서만 그러셨을 수 있다.

**규칙 TI-7.** 최대 **7줄.** 넘으면 편 수가 적은 것부터 지운다.
길어지면 writer 가 다 못 지키고, 못 지킬 지시는 없느니만 못하다.

**규칙 TI-8.** 시그니처·클리셰는 여기 적지 않는다. `표현사전.json` 이 맡는다.
편집률 추이도 적지 않는다. `_발행대장.json` 이 맡는다.
**같은 사실을 두 곳에 적으면 두 곳이 엇갈린다.** 여기는 *습관*만.

**규칙 TI-9.** 관찰은 **행동으로 적는다.** "문장이 짧다" 가 아니라
"긴 문장을 두 개로 쪼개신다". writer 가 그대로 실행할 수 있어야 뜻이 있다.

### 이 섹션이 없어도 글은 나온다

없으면 writer 는 그냥 목표치만 보고 쓴다. 첫 글부터 있을 수 없는 섹션이다.
**없다고 경고하지 않는다.** 원장님이 아직 고쳐주신 적이 없다는 뜻일 뿐이다.

## 7. 온보딩 화면 흐름

```
[톤 설정] 원장님 말투를 배우겠습니다

  가지고 계신 걸 아무거나 주세요. 형식은 상관없습니다.

  ┌──────────────────────────────────────┐
  │  파일 끌어다 놓기                      │
  │  (글·PDF·워드·카톡 내보내기 다 됩니다)  │
  └──────────────────────────────────────┘
       또는  [블로그 주소 입력]  [직접 붙여넣기]

  아무것도 없으신가요?  →  [예시 보고 고르기]
```

**한 번에 다 요구하지 않는다.** 하나만 넣어도 다음 단계로 넘어가고,
나중에 더 넣으면 톤가이드가 좋아진다고 안내한다.

## 8. 구현 순서

| 단계 | 내용 | 시점 |
|---|---|---|
| 1 | 형식 로더 (txt/md/pdf/docx/카톡csv/카톡txt) | M2 |
| 2 | 카톡 화자 분리 + 확인 UI | M2 |
| 3 | PII 마스킹 + 확인 화면 | M2 |
| 4 | 표본량별 신뢰도 표기 | M2 |
| 5 | 프리셋 3종 | M2 |
| 6 | 발행 후 학습 루프 | M5 |

## 9. 검증 방법

| 항목 | 테스트 |
|---|---|
| 형식 로더 | 6개 형식 각 1개 파일 → 텍스트 추출 성공 |
| 화자 분리 | 3인 이상 단톡 → 화자별 발화 수 정확 |
| 자동 추정 | 원장 이름을 기초정보에 넣은 경우 → 1순위 추천 적중 |
| PII 마스킹 | 이름·전화·학교 심은 테스트 대화 → 검출률 100% |
| 프리셋 | 프리셋만으로 글 생성 → 검수 게이트 통과 |
